Read-only audit 2026-09-20 of both consumers named in mdkb/CLAUDE.md. THE APP uses exactly five daemon-socket RPC methods and no others (swept the whole tree): ping, symbols_in_file, symbol_at_position, code_graph, code_find. It is on the HOOK socket resolver (src/daemon/hook_runtime.rs:120-136), which requires params.root as an absolute path and hands it straight to registry.get_or_open - NOT the MCP resolver (src/mcp/server.rs:560) where root='*' already works. Consequence for any root-grammar work: keep the grammar on the MCP side, or an absolute path containing a comma becomes ambiguous under a comma-list grammar and a repo NAME could shadow a same-spelled path. Neither guard exists. Version compatibility is exact equality, not a floor (mdkb_daemon.rs:128-134) against CARGO_PKG_VERSION, so any version bump forces 'mdkb daemon restart' on the first call, and renaming that subcommand or changing its exit code takes all five features dark at once. THE PLUGIN shells out to '--format json' at four sites in plugins/mdkb-dashboard/main.js: stats (:54 and the :552 ticker), memory list (:55), and the ACTIONS set (:465). Read by nothing: memory.files_unreadable, memory.entries_unprojected, code.relations_by_kind, code.top_files, hooks.drift, hooks.mining.*, hooks.events[].converted, quarantine. HOW BOTH FAIL: silently. The app's with_client turns every error into None plus a warn! log and each command does unwrap_or_default, so a broken shape shows an empty outline or no references, never a dialog. Only code_graph has a shape guard (a missing 'symbols' key is a deliberate hard error distinct from []); the other three flatten a parse failure to [], so 'mdkb changed shape' and 'no symbols here' are identical. In the plugin the ONLY loud failure is unparseable stats stdout, which replaces the dashboard with 'mdkb not available'. The memory branch has no else at all: when 'memory list' exits non-zero the promise rejects, data.memories stays null, data.error is never set, and the panel renders 'No memory entries yet' next to a badge row still showing live counts from stats. That fired for real on 2026-09-20: the salvage column-order bug put text in last_refuted_at, every memory read goes through row_to_entry_offset (src/store/memory.rs:2273, row.get(off+15)?), so memory list exited non-zero all day while the badge said 119. TWO SILENT-NUMBER TRAPS: code_find is capped at limit.unwrap_or(50) and mdkb ships total+showing precisely so a capped list cannot read as the whole set - TUIC parses both and DISCARDS them (mdkb_client.rs:32-34) and sends no limit, so changing that default changes a displayed count with no shape change. And the 0-based to 1-based conversion is a bare +1 at mdkb_commands.rs:51-53; normalising symbol_to_json's line_start would make every jump land one line late while TUIC's own tests keep passing, because they assert the shift, not the source convention.
