Cross-folder flows

MDKB keeps one store for one project. The folder you start from never decides what answers you — a rule decides, and the rule states what it covered. This page lists every cross-folder flow that is implemented, the rule each one applies, and the failure each one prevents.

1 : 1One project, one store. Never one store for a tree of projects.
N of MA fan-out states its coverage. An empty answer is never silent.
read-onlyReading another repo takes no handle and evicts nothing.

1. Where the store is — anchor resolution live

Every command starts by answering one question: which .mdkb/ owns this working directory? The answer must not change when you move to a subfolder, and it must not expand when you move up.

GuardRuleWhat it stops
holds_git_repos True when any immediate child holds .git. It sees a directory and a worktree file alike. A store on a container of repos, which indexes every repo below it.
is_home_or_above True for $HOME and every ancestor of it. A store that anchors everything the user owns. $HOME usually has no repo as an immediate child, so the container test alone lets it through.
over_anchors Either of the two above. Applied to the adopted store, to the hint, and to the bare cwd. Refusing to adopt a container store while creating one in the same directory.
Measured. With no guard on the fallback, a session started in ~/Gits created ~/Gits/.mdkb: 2.9 GB in nine minutes, ten cores at 100% for 24 hours (2026-08-19). A store at $HOME was measured at 1.2 GB indexing the whole home directory.

When every candidate would over-anchor, the command stops and says so. It does not fall back to a smaller guess:

Error: refusing to anchor a store at /.../home: it holds git repositories
(or is your home directory), so a store here would index every repository
underneath it. Run mdkb from inside a project, or `mdkb init` here if you
really mean it.

mdkb init is the one command that bypasses the rule, so an operator who means it can still create the store. Every later command still applies the rule, so an init against the rule produces a store that nothing reads.

src/git.rs — resolve_project_root (541), find_project_store_above (499), over_anchors (468), holds_git_repos (440), is_home_or_above (454)

2. Worktrees collapse to one store live

The chosen directory is collapsed to the main worktree. Every worktree of a repository reads and writes the same store, so a feature branch checked out beside the main tree inherits the knowledge instead of starting empty. The anchor is immune to drift inside the repo: cwd is only a starting point for the bounded walk.

src/git.rs — resolve_main_worktree

3. Folder scoping inside one store — collections live

A collection is a name, a path below the store root, and a glob. It is how one store holds many folders without mixing them in search.

mdkb collection add rfc ./engineering/RFC '**/*.md'
mdkb search "capacity model" -c rfc --limit 5
BehaviourDetail
Path traversal is blocked A path that resolves outside the root is refused. When the path does not exist yet, a literal .. is refused.
collection update --pattern keeps the documents Fixing a glob no longer drops every row and re-embeds the folder. The next mdkb update reconciles incrementally.
collection update --path does not carry rows over A document is keyed by its path relative to the collection base. A new base is indexed from scratch.
Auto-registration by convention [conventions] enabled registers collections that follow the layout. The upsert makes it safe against a concurrent manual collection add.
src/core/graph.rs — validate_collection_path (142); src/store/collections.rs — add_collection

4. The knowledge graph is per store live

Edges live in the store that indexed the document. mdkb graph filters by relation and by nothing else — there is no collection filter and no scope filter. hubs, dangling, neighbors and path read the whole store.

This is a design statement, not a gap. Two bodies of knowledge that must not mix belong in two stores. Collections divide search; only a store boundary divides the graph.

Target references are stored verbatim and resolved at query time, so indexing order does not matter. Resolution tries the reference, then without a leading ./ or /, then with .md added or removed, then all of those again with a leading collection name stripped. So map/people/alice and people/alice.md reach the same document.

Paths are not the only way a reference resolves. When every path form has missed — and only then — resolution falls back to the identities a document declares for itself in frontmatter (id: and aliases:, configurable as graph.identity_keys). That is what makes person:alice reach people/alice.md on a typed corpus. The order is load-bearing: a reference naming a real file keeps naming that file even when another document claims the same string as an alias. Identities are per store, like edges, so a name declared in one store never resolves from another.

Two documents claiming one identity is a repository defect rather than an index failure: resolution takes the lowest document id deterministically and the collision stays reportable.

5. Fan-out across repositories — cross-repo search live

One query, every repository the daemon knows. This is the flow that makes many small stores better than one large one: isolation by default, reach on request.

The coverage footer is always emitted, including when every repo was searched.

The root grammar

FormMeaning
omittedThe workspace the client declared, and every store nested beneath it. search fans out over all of them; a single-target tool means the workspace itself when that path is a store, and refuses when it anchors none.
root="/abs/path"One repo by path. It need not be a known repo.
root="name"One repo by name — the last component of a known root.
root="name,/abs/path"Several repos. Names and paths mix freely.
root="*"Every known repo. It cannot be combined with other terms.

A comma is always the separator. A path that contains one is ambiguous, so it is refused by name instead of split into two selectors that resolve to nothing. An absolute path and a name are told apart syntactically, before anything is looked up, so a repo name can never shadow a path.

What the fan-out guarantees

GuaranteeWhy it matters
Known, not open Open handles are an LRU capped at max_active_repos and empty after a restart. Fanning out over them omits every known but closed repo, silently.
Read-only open No handle, no watcher, no LRU slot taken from the repo the caller is working in.
A skipped repo is named A store this binary cannot read is reported with its reason. It is never counted as empty.
Coverage is stated Without the denominator, "no results" means both "nothing matched" and "never looked".
Only search fans out Code, symbols and duplicate indexes are per-repo. Those scopes are rejected with a message that asks for a root.
The CLI stays local root is an MCP parameter. The CLI always works in the current repo.
src/daemon/repo_map.rs; src/mcp/dispatch.rs — cross_repo_search_impl (1666), format_cross_repo_coverage (1636); src/mcp/tools.rs — the root grammar

Health of a known root

The map records why a root did not answer, and the distinction is the point of the type. A store that cannot be read is a property of this binary, of a lock, or of file permissions. It is never evidence that the repository was deleted.

StateMeaning
HealthyThe root is there and its store can be listed.
GoneNothing exists at that path any more. The root is dropped.
NoStoreThe path exists and holds no .mdkb.
Unreadable(reason)The store is there and this process cannot read it.

The map is written whole through temp and rename, so no reader sees a half-written file. No cross-process lock is taken: a writer holding an older set can drop a root another process just recorded, which costs one re-record on the next open.

6. Read-only layering onto ancestor stores implemented, not wired

discover_ancestor_stores walks up from a store and collects the ancestors that already hold a .mdkb, nearest first, capped by depth. It never creates anything and never includes the store itself, so layering can add read provenance without bringing store proliferation back.

It has no caller outside its tests. A nested repository does not inherit its parent's knowledge today. Treat two stores as hermetic.

src/git.rs — discover_ancestor_stores (564)

7. A worked example

A planning workspace that is not a git repository, with two branches that must not mix:

brainstorming/          not a git repo
├── work/               .mdkb  ← 306 docs, 28 collections, 182 edges
│   └── graph/          people, orgs, meetings, decisions, initiatives
├── home/               no store
│   ├── monfumo/        .git + .mdkb   ← own store
│   ├── investimenti/   .git + .mdkb   ← own store
│   └── twitter/        .mdkb          ← own store
└── tools/              shared scripts
Run fromStore that answersRule
work/work/.mdkbNearest ancestor store that is a project.
work/engineering/RFC/work/.mdkbSame. A subfolder rediscovers its own store.
home/monfumo/monfumo/.mdkbInside a repo. The store at the repo root wins.
home/twitter/twitter/.mdkbNot a repo, holds no repos, has a store.
home/refusedhome/ holds monfumo/.git and investimenti/.git as immediate children.
The trap this makes visible. Put a store at brainstorming/.mdkb and home/ adopts it, because brainstorming/ has no repo as an immediate child. The store stays empty, every memory add run from home/ lands in it, and nothing ever reads it. Removing that store turns a silent write into a loud refusal.

To give home/ a branch store of its own, the two repositories have to stop being its immediate children — for example under home/projects/. The guard reads one level, by design: a deeper scan would make the anchor depend on how far down someone cloned a repository.
